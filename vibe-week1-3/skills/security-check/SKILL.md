# Security Check

HTML/JS 파일을 대상으로 아래 4가지 관점에서 보안 취약점을 점검하고, 등급과 파일:라인 근거를 포함한 보고서를 작성한다.

## 점검 대상 파일 고르기

Glob으로 `*.html`, `*.js` (및 `.jsx`, HTML 안의 inline `<script>` 블록)를 수집한다. 사용자가 특정 파일이나 디렉터리를 지정했으면 그 범위로 좁히고, 지정하지 않았으면 현재 작업 디렉터리 전체를 대상으로 한다.

## 4가지 점검 항목

각 항목은 기계적 정규식 매칭이 아니라 판단 기준으로 접근한다. 아래 패턴은 후보를 찾기 위한 출발점(Grep)일 뿐이며, 실제 위험 여부는 문맥(Read)으로 반드시 확인한다.

### 1. 하드코딩된 비밀번호 / API 키
`password`, `pwd`, `apikey`, `api_key`, `secret`, `token`, `accessKey` 같은 이름의 변수·속성에 리터럴 문자열이 직접 대입되어 있는지 찾는다.
- 위험 신호: `sk-`, `AKIA`, 긴 무작위 문자열, 실제 이메일/도메인이 포함된 값처럼 보이는 경우
- 오탐 배제: `"YOUR_API_KEY_HERE"`, `"changeme"`, `""`, 환경변수 참조(`process.env.X`)처럼 실제 값이 아닌 플레이스홀더는 제외
- 왜 위험한가: 소스에 박힌 키는 저장소를 보거나 배포된 정적 파일을 열어보는 누구에게나 그대로 노출된다.

### 2. escape 없이 innerHTML에 들어가는 사용자 입력 (XSS)
`.innerHTML =` (또는 `.innerHTML +=`, `outerHTML`) 대입의 우변을 추적해서, 그 값이 사용자가 통제할 수 있는 출처에서 왔는지 확인한다.
- 사용자 입력 출처 예: `location.search`, `location.hash`, `URLSearchParams`, `<input>`/`<textarea>`의 `.value`, `prompt()`, URL 쿼리 파싱 결과, 서버 응답 중 사용자가 작성한 텍스트
- 안전하게 처리된 경우(취약점 아님): `textContent`/`innerText`로 대입, DOMPurify 같은 sanitizer를 거친 값, HTML 엔티티 이스케이프 함수를 통과한 값
- 왜 위험한가: 공격자가 URL이나 입력값에 `<script>` 등을 넣으면 그대로 실행되어 세션 탈취, 피싱 등으로 이어질 수 있다.

### 3. console.log의 민감정보 노출
`console.log`(및 `console.debug`, `console.info`) 인자에 비밀번호, 토큰, 세션 정보, 개인정보(주민번호·전화번호·이메일 등)로 보이는 변수나, 그런 값을 포함할 가능성이 높은 객체 전체(`user`, `req.body`, `response.data` 등)가 그대로 찍히는지 확인한다.
- 왜 위험한가: 브라우저 콘솔이나 서버 로그에 민감정보가 평문으로 남으면 로그 접근 권한이 있는 사람 누구에게나 노출된다.

### 4. http://로 시작하는 외부 요청
`fetch(`, `XMLHttpRequest`, `axios.get/post`, `<script src=`, `<img src=`, `<link href=` 등에서 `https://`가 아닌 `http://` 외부 호스트를 사용하는지 확인한다.
- `http://localhost`, `http://127.0.0.1` 등 로컬 개발 주소는 실제 위험이 낮으므로 등급을 낮추거나 참고 수준으로만 언급한다.
- 왜 위험한가: 평문 HTTP는 중간자 공격(MITM)에 노출되어 통신 내용이 도청·변조될 수 있다.

## 등급 매기기

고정된 규칙이 아니라 기본 가이드다. 같은 항목이라도 실제 노출 범위와 악용 난이도에 따라 등급을 올리거나 내려도 된다.

- 🔴 심각 — 기본적으로 하드코딩된 비밀번호/API 키, 실행 가능한 XSS
- 🟡 주의 — 기본적으로 console.log 민감정보 노출, http:// 평문 외부 요청
- 🟢 제안 — 위 4가지에 명확히 해당하지는 않지만 개선하면 좋은 사항(예: CSP 미설정, http를 https로 전환 권장, 입력 검증 강화 등). 취약점이 전혀 없을 때도 이 등급으로 개선 아이디어를 남긴다.

## 보고서 형식

찾은 내용을 아래 형식 그대로 정리한다. 근거 없는 지적을 하지 않도록, 각 항목마다 반드시 `파일:라인`과 실제 코드 스니펫을 인용한다. 각 등급에 해당 사항이 없으면 그 섹션은 생략한다.

```
## 보안 점검 결과

🔴 심각 — <문제 요약>
`<파일 경로>:<라인>` — `<해당 코드 한 줄>`
이유: <왜 위험한지, 어떻게 악용될 수 있는지 한두 문장>
제안: <간단한 수정 방향>

🟡 주의 — <문제 요약>
`<파일 경로>:<라인>` — `<해당 코드 한 줄>`
이유: ...
제안: ...

🟢 제안 — <개선 아이디어>
`<파일 경로>:<라인>` (해당하는 경우)
...
```

발견된 문제가 하나도 없다면 "🔴/🟡 항목에서 특별한 문제를 찾지 못했습니다"라고 명시하고, 그래도 가능하면 🟢 제안 한두 개를 남긴다.

## 작업 순서

1. Glob으로 대상 파일 목록을 만든다.
2. 항목별로 Grep을 돌려 후보 라인을 모은다 (예: `innerHTML`, `console\.(log|debug|info)`, `http://`, `password|secret|token|api[_-]?key` 등 키워드).
3. 후보가 나온 파일은 Read로 주변 문맥을 읽어 실제로 위험한지, 오탐인지 판단한다.
4. 등급별로 묶어서 위 보고서 형식대로 작성한다.
